# Career Bot — передача контекста Codex, 2026-09-05

## Цель и пользователь

Александр Плюцак, студент, ищет стажировки/junior-роли. Цель: уйти на 1–2 часа и получить 100+ разобранных вакансий и письма для подходящих, затем пакетно подтвердить отклики. Продукт локальный: Python + SQLite + Ollama/Qwen + расширение Edge для hh.ru. Пользователь не программист; нужны конкретные действия и понятные результаты. Внешние ИИ API пока не используются. Новое разрешение на реальные отправки не следует выводить из просьбы проверить диагностику.

## Версии и запуск

Сервер APP_VERSION 0.21.5; scripts/launch-career-bot.ps1 ExpectedVersion 0.21.5; расширение manifest 2.3.6. При изменении сервера синхронизировать версию запускателя, иначе он может сохранить старый процесс. Расширение обновляется отдельно с перезагрузкой вкладок. Python 3.12, стандартная библиотека, Windows. Порт 8765; Ollama обычно 11434. QUICK_START_NEW_PC.md — актуальная инструкция, старые README/документы могут описывать уже отключённые функции.

## Файлы и данные

- career_bot/server.py (~3850 строк): HTTP, SQL, профиль, поиск, скоринг, подбор фактов, промпты, валидация, очереди, отправка.
- career_bot/static/app.js: интерфейс, прогресс партий, подтверждение писем, диагностика.
- hh-career-bot-extension/content.js: импорт профиля, сбор полных вакансий, старая логика отправки.
- background.js: связь с локальным сервером и загрузка вакансий через вкладки.
- diagnostic.js: диагностика по hash careerBotDiagnostic, без кликов по кнопкам сайта или отправок.
- data/career_bot.sqlite: users, user_profiles, vacancies, events, ai_settings, letter_jobs/letter_batches, apply_sessions/apply_batches, search_runs/search_scenarios.
- tests/test_apply_recovery.py и test_diagnostic_safety.py: всего 5 небольших тестов. Они не доказывают работоспособность реального HH.

Данные в архиве сняты через SQLite backup. В КОПИИ удалены sessions и apply_sessions, внешние ключи; активные очереди остановлены. Оригинал не менялся. Модели и окружение нужно установить отдельно. Архив содержит персональные данные; не публиковать.

## Что требуется от писем

Русский язык, мужской род, без «(а)», плейсхолдеров, двойного приветствия/подписи и канцелярита. Основа: релевантный опыт → личное действие → результат; числа только из соответствующего опыта, без выдумок и присвоения требований работодателя. Хакатон/учебный кейс не называть работой в компании. Oasis — коммерческий логистический опыт (около 2000 заказов за 5 месяцев); Solutions — самостоятельное исследование; X5/Ростелеком/Alfa/Калининград — кейсы/хакатоны. Точные факты брать из перенесённого профиля, не восстанавливать по памяти.

Стратегия поиска отдельна от опыта: интерес к junior project/product/marketing/research/operations, гибкости и развитию. Запреты должны учитывать контекст. Целевые пороги 65–79 короткое письмо 700–1100 знаков; 80+ глубокое 1200–1800. Цель 100 писем/2ч требует среднего времени около 72с включая обработку; фактическая производительность не подтверждена.

## Состояние отправки — критично

Массовая автоотправка ОТКЛЮЧЕНА на сервере, в UI и content.js после реального сбоя: пользователь сообщил, что 10 откликов ушли без писем; отчёт Career Bot показывал 0 отправлено, 6 ручная проверка, 4 пропущено. Не убирать заглушки только ради запуска. Реальная отправка после переработки ещё не проверена.

HH имеет три пути: поле письма сразу; уже созданный отклик и «Приложить сопроводительное письмо» ниже; чат соответствующей вакансии. Вопросы/тесты/мини-интервью пока ручные. Не отвечать за пользователя. PDF пока не добавлять автоматически.

Старый runSimpleBatchApply: первый клик может отправить отклик сам по себе, далее отсутствие поля приводит к needs_manual и переходу дальше. clickAddCoverLetter/openEmployerChat в этой цепочке не используются. Успех ищется по общим фразам всей страницы. Нет надёжной привязки подтверждения письма к вакансии. Нужно отдельно хранить состояние отклика и доставки письма; неизвестный результат нельзя автоматически повторять.

pause_apply_batch/resume_apply_batch умеют переводить running в ручную проверку, истекать старые токены и возобновлять только pending с новыми токенами. При запуске сервера активные партии приостанавливаются. Сейчас отправка и возобновление заблокированы.

## Диагностика и проверенные наблюдения

POST /api/vacancies/<id>/diagnostic-session создаёт 15-минутную ссылку; GET /api/apply/session/<token> отдаёт одобренное письмо; POST .../diagnostic пишет event_type apply_diagnostic. Последние отчёты можно читать прямо в SQLite, не печатая токены/переписку.

Наблюдавшиеся data-qa:
- responded-success-attach-cover-letter — «Приложить сопроводительное письмо»;
- vacancy-response-popup-form-letter-input — textarea name=text в role=dialog;
- vacancy-response-link-view-topic — «Чат» (несколько экземпляров);
- vacancyResponses-button — общий заголовок «Отклики», не кнопка нужной вакансии.

Событие 126 для Midle Delivery Lead: after_fill, fieldCount=1, exactLetterMatch=true. Это совпадение значения DOM через 700мс, НЕ подтверждение визуального результата или отправки. Пользователь позже сообщил, что ничего не вставилось. Не объявлять этот сценарий готовым.
Событие 151 (2026-09-04 17:53:05 UTC), Маркетолог с фокусом на блогеров: v2.3.6, manual_capture, полей 0. Скрин показывал робота-рекрутера с вопросом и кнопками да/нет, а также ссылку «Добавить сопроводительное» под отправленным откликом. Ранее ассистент без достаточных доказательств назвал вопрос причиной отсутствия поля. Это гипотеза, не установленный факт.

Диагностика 2.3.6 ищет textarea/contenteditable=true/role=textbox только в основном document, исключает disabled/readonly, не исследует iframe/shadow DOM, берёт первые 30 кнопок по тексту. Поэтому 0 полей не доказывает блокировку вопросом, а финальная кнопка может не попасть в отчёт. При расширении диагностики сначала собирать метаданные контейнера/всех полей (включая недоступные и причину), без содержимого переписки. Не вставлять письмо в произвольный единственный textbox: нужна идентификация назначения и вакансии.

## Результаты аудита 5 сентября — ещё НЕ реализованы

1. score_vacancy блокирует любое «5/2», «релокац», «холодн» и т.п. без контекста/отрицаний. strategy_hard_stops и priorities хранятся, но скоринг задаёт собственные маркеры. assess_eligibility применяет отдельные правила/пороги. Нужен единый результат допуска и объяснений.
2. build_experience_records делит текст по строкам с датами, действия по маркерам списка. Изменение оформления ломает карточки. Нужна постоянная библиотека проверенных фактов с ID, источником, типом опыта, действием, результатом и ограничениями.
3. build_letter_evidence_plan — словари/пересечения, не LLM-разбор. Бонусы за числа и действия допускают нерелевантные факты; даты тоже считаются числами. Нужна привязка факта к требованию; локальный структурированный разбор и кэширование стоит оценить на тестовом наборе.
4. validate_ai_letter разрешает числа/латинские названия из профиля И вакансии, новые детали лишь warning. Это позволяет присвоить требования работодателя. letter_quality вычисляется по стилю без полного учёта evidence warnings. Нужна проверка утверждений о кандидате по конкретным источникам и единый статус качества.
5. LETTER_GENERATION_TIMEOUT=300, но HTTP Ollama timeout=180. run_with_timeout использует daemon thread и join; истечение ожидания НЕ завершает поток. Нужен единый бюджет и реальная отмена/управление задачами. Сейчас один letter_queue_worker; преждевременно увеличивать параллелизм на GPU не стоит.
6. Отправка требует устойчивых переходов между состояниями, а не последовательности угадываемых кликов. Доставка письма и отклика учитываются раздельно, подтверждение связано с конкретной вакансией/версией письма.
7. Нужен модульный монолит: профиль/факты, вакансии/сбор, оценка, письма/валидация, очередь, адаптер HH, журнал. SQLite и Python оставить. Не делать полную перепись ради структуры.

Рекомендуемый порядок: исправления скоринга/достоверности → стабильная библиотека опыта → 20–30 эталонных вакансий и измерение качества/времени → надёжная очередь → три сценария HH и восстановление → партии 10/30/100. Этот аудит был только обзором; пользователь следующим запросом попросил подготовить перенос, а не реализовать аудит.

## Как продолжать

Сначала прочитайте актуальный код и инструкции запуска, проверьте базу и установленную Ollama. Согласуйте следующий объём работы по текущему запросу пользователя. Не воспринимайте исторические обещания ассистента как доказательства реализации. Для проверок используйте временную БД/fixtures; не запускайте реальную рассылку как тест. Не публикуйте личные данные и не стирайте исходную базу. Сообщайте отдельно: что проверено кодом, что наблюдалось на HH, что остаётся гипотезой.
